# Tempestas: Wind Energy Production and Price Prediction System

## Project Overview

Tempestas is a comprehensive two-stage machine learning system designed to predict hourly wind energy production (both offshore and onshore) and subsequent wholesale electricity prices in the Netherlands. It leverages a combination of meteorological data, historical energy generation records, and electricity market pricing to provide accurate forecasts.

The system operates in two distinct stages:

1.  **Stage 1: Wind Power Production Prediction:** A Temporal Convolutional Network (TCN) model forecasts hourly wind energy generation based on detailed weather variables and historical production patterns.
2.  **Stage 2: Electricity Price Prediction:** An XGBoost regression model utilizes the predicted wind energy output from Stage 1, along with temporal features and lagged price data, to predict hourly wholesale electricity prices.

## System Architecture

The Tempestas system employs a sequential modeling approach:

### Stage 1: Wind Power Prediction (TCN Model)

* **Objective**: Predict normalized hourly offshore and onshore wind energy production (MW).
* **Model**: Temporal Convolutional Network (TCN). TCNs are well-suited for sequence modeling tasks due to their ability to capture long-range temporal dependencies using dilated convolutions, process sequences in parallel, maintain causality, and handle long sequences efficiently.
* **Input Features**:
    * Historical weather variables (wind speed, direction, temperature, pressure, humidity, cloud cover, rainfall - see Dataset Description for details).
    * Temporal features (e.g., hour, day of week, cyclical encodings).
    * Lagged energy production values.
* **Target**: Normalized offshore and onshore wind energy production.
* **Key Architecture Details**:
    * Input sequence length: 12 hours.
    * Input features: 21.
    * TCN Layer: 16 filters, kernel size 9, dilations [1, 2, 4, 8, 16].
    * Residual Blocks: 4 stacked blocks with skip connections.
    * Regularization: Dropout rate of 0.3.
    * Output Layer: Dense layer with linear activation.
    * Optimizer: Adam with a learning rate of 0.001.

### Stage 2: Electricity Price Prediction (XGBoost Model)

* **Objective**: Predict the hourly wholesale electricity price ($EUR/MWh$).
* **Model**: XGBoost (Extreme Gradient Boosting) regression model. XGBoost is chosen for its robustness, ability to handle non-linear relationships and feature interactions effectively, and strong performance on tabular data.
* **Input Features**:
    * Predicted offshore and onshore wind energy production (output from Stage 1).
    * Temporal features
    * Lagged electricity price values
* **Target**: Wholesale electricity price ($EUR/MWh$).
* **Key Architecture Details**:
    * Estimators: 1000 maximum (with early stopping based on validation performance).
    * Learning Rate: 0.017.
    * Maximum Depth: 7.
    * Subsample: 0.7.
    * Regularization: L1 (alpha: 0.17) and L2 (lambda: $3.76 \times 10^{-6}$).

## Data Sources

The system utilizes data from several publicly available sources:

1.  **Weather Data**:
    * **Source**: Open-Meteo Historical Weather API (`https://open-meteo.com/en/docs/historical-weather-api`)
    * **Scope**: Hourly data from 2017-2025 for 23 wind turbine clusters (9 offshore, 14 onshore) across the Netherlands.
2.  **Energy Production Data**:
    * **Sources**:

        * ENTSO-E Transparency Platform (`https://transparency.entsoe.eu/dashboard/show`) - Actual generation per production type.

3.  **Electricity Price Data**:
    * **Source**: Ember Energy Data Repository (`https://ember-energy.org/data/european-wholesale-electricity-price-data`)
    * **Scope**: Hourly wholesale electricity prices ($EUR/MWh$) for the Netherlands, 2015-2025.

## Dataset Description

### Weather Data

Sourced via the Open-Meteo Historical Weather API, this dataset provides hourly meteorological variables crucial for wind power prediction. Data is collected for 23 distinct wind turbine cluster locations within the Netherlands. Key variables include:

* Wind speed at 100m and 10m heights ($m/s$).
* Wind direction at 100m and 10m heights (degrees).
* Wind gusts at 10m ($m/s$).
* Surface pressure ($hPa$).
* Temperature at 2m ($^{\circ}C$).
* Cloud cover (low, mid, high levels) (%).
* Relative humidity (%).
* Rainfall ($mm$).

Data fetching is managed by the `load_data.py` script, incorporating error handling, API rate limiting, and response caching for efficiency.

### Energy Production Data

This dataset quantifies the actual electricity generated by wind turbines. It combines data from NED.NL (for specific offshore/onshore splits) and the ENTSO-E Transparency Platform (for overall generation figures).

* **Frequency**: Hourly.
* **Unit**: Megawatts (MW).
* **Structure**: Time series separated into `Wind_Offshore_MW` and `Wind_Onshore_MW`.
* **Period**: 2017-2025 (aligned with weather data).

### Electricity Price Data

Obtained from Ember Energy, this dataset contains the hourly clearing price for wholesale electricity in the Dutch market.

* **Frequency**: Hourly.
* **Unit**: Euros per Megawatt-hour ($EUR/MWh$).
* **Period**: 2015-2025.

## Data Processing Pipeline

Raw data from the sources undergoes several processing steps to create the features needed for the models.

### Initial Data Collection

* Weather data is fetched programmatically using `load_data.py` for defined coordinates.
* Energy production and price data were acquired manually from their respective portals and stored locally.

### Data Preprocessing (`preprocess_data_script.py`)

This script performs initial cleaning and standardisation:

* **Time Zone Conversion**: Ensures all timestamps are aligned to UTC.
* **Feature Engineering (Initial)**: Cyclical encoding of temporal features (hour, day of week, month, day of year) using sine and cosine transformations to capture cyclical patterns. Wind direction is also cyclically encoded.
* **Missing Value Handling**: Imputation or interpolation methods are applied as appropriate (e.g., linear interpolation for time series gaps).

### Data Combination and Aggregation (`combine_data.py`)

This script merges and aggregates weather data:

* Combines data from multiple weather stations relevant to offshore and onshore clusters.
* Computes average weather conditions across these clusters.
* Ensures time-based alignment across different data streams.

### Final Feature Engineering (`/wind/power/prediction/data_processiong.py` and model-specific scripts)

Further feature engineering prepares the data for model input:

* **Rolling Capacity Proxy**: Calculation of a proxy for installed wind capacity (e.g., using rolling maximums of production) to normalize the wind power output signal. This helps the model focus on the relationship between weather and the *proportion* of available capacity being utilized.
* **Normalization**: Wind power output is normalized (e.g., using the capacity proxy or standard scaling methods).
* **Lagged Features**: Creates lagged versions of target variables (energy production for Stage 1, price for Stage 2) to capture autocorrelation.

## Model Details

### Wind Power Prediction (Stage 1 - TCN)

* **Hyperparameter Tuning**: A hyperparameter search was conducted using `azure_hyperparameter_tuning.py` on Azure cloud compute instances. This involved a random search over parameters like sequence length, filter count, kernel size, dropout rate, L2 regularization, learning rate, and batch size to find the optimal TCN configuration. The best parameters found were stored and used for the final model.
* **Training**: The TCN model was trained on data starting from 2020-01-01, using a chronological split for validation to prevent data leakage from the future. Input features are scaled (e.g., using `RobustScaler`), and the target (normalized wind production) is predicted.
* **Inference**: During inference (`wind_generation_tcn_inference.ipynb`), the trained model takes recent weather and production data sequences as input, predicts the normalized output, which is then denormalized back into MW using the calculated capacity proxy and saved scalers.

### Electricity Price Prediction (Stage 2 - XGBoost)

* **Training**: The XGBoost model is trained using the predicted wind energy production from Stage 1, along with temporal features and lagged price features. Training incorporates early stopping based on performance on a validation set to prevent overfitting.
* **Feature Importance**: Analysis of the trained XGBoost model revealed the most influential features for predicting Dutch electricity prices:
    1.  Predicted Offshore Wind Energy Production (from Stage 1)
    2.  Price Lag 1 hour (`price_lag_1h`)
    3.  Hour of the Day (cyclical encoding)
    4.  Predicted Onshore Wind Energy Production (from Stage 1)
    5.  Day of the Year (cyclical encoding)

## System Performance

This section details the performance of both stages of this project.

### Stage 1: Wind Power Prediction Performance & Capacity Proxy

A key challenge in predicting wind power over several years (2017-2025) in the Netherlands is the significant growth in installed wind capacity during this period. Predicting raw Megawatt (MW) output directly is difficult because the maximum potential output changes substantially over time.

To address this, a **Capacity Proxy** was calculated to estimate the operational capacity at any given time. This was achieved by:
1.  Calculating the total hourly wind power (`Total_Wind_MW` = `Wind_Offshore_MW` + `Wind_Onshore_MW`).
2.  Applying a rolling maximum over a long window (365 days) to this total power. This rolling maximum serves as an approximation of the installed capacity.

The following graph shows the calculated capacity proxy (green line) plotted against the original offshore (blue) and onshore (red) wind power generation. The upward trend of the green line clearly illustrates the increasing installed capacity over the years.

![Calculated Capacity Proxy vs Original Power](images/capacity_proxy_vs_power.png)

The actual wind power outputs (Offshore MW and Onshore MW) were then **normalized** by dividing them by this capacity proxy. This transforms the prediction target for the TCN model into a value representing the proportion of the estimated capacity being utilized (effectively a capacity factor, typically between 0 and 1).

This normalization step is crucial because it allows the TCN model to focus on learning the complex relationship between weather patterns and the *efficiency* of wind power generation, independent of the total installed capacity at that specific time. The model predicts this normalized output, which is then denormalized back to MW using the proxy for downstream use in Stage 2.


#### TCN Model Training and Evaluation

The TCN model was trained to predict the normalized wind power output. The training progress, showing the decrease in loss (Scaled Normalized MSE) and Mean Absolute Error (MAE) on both the training and validation sets over epochs, is displayed below. The close tracking of validation metrics with training metrics indicates good generalization without significant overfitting.

As shown, the TCN model significantly outperforms the 24-hour persistence and simple average baselines. It also achieves a lower MAE and RMSE compared to the 1-hour persistence baseline, demonstrating its effectiveness in capturing the complex dynamics of wind power generation based on weather inputs beyond simple lagged values.

The predicted MW output from this stage serves as a crucial input for the Stage 2 price prediction model.

### Stage 2: Electricity Price Prediction (XGBoost)

With the normalized wind power predictions from Stage 1 (now denormalized back to MW using the capacity proxy), this stage focuses on the core task of predicting hourly electricity prices (EUR/MWh) for the Dutch market. Electricity prices are highly volatile, influenced by supply (including renewables like wind), demand, and other market factors.

An **XGBoost (Extreme Gradient Boosting)** model was chosen for this regression task due to its performance and efficiency with structured data. The model is trained using a combination of features designed to capture the dynamics of the electricity market:

1.  **Predicted Wind Power:** The estimated wind energy generation (in MW) from Stage 1 serves as a crucial input reflecting renewable supply.
2.  **Temporal Features:** Time-based features like hour of the day, day of the week, etc., are included to model cyclical patterns in demand and pricing.
3.  **Lagged Price Features:** Past electricity prices (e.g., price 1 hour ago, 24 hours ago) are used, as current prices are often strongly correlated with recent historical prices.

## Tempestas Implementation Guide: End-to-End Process

This guide outlines the steps to run the Tempestas system, potentially adapting it for your own similar dataset or region.

**1. Data Collection**

* **1.1. Weather Data Collection:**
    * Identify the latitude/longitude coordinates for your wind farm locations or relevant weather points. (This, in my case, had to be done manually (with the help of governamental documents and Google Maps)
    * Update the location configurations within `data_processing/load_data.py`.
    * Run the script to fetch historical weather data: `python data_processing/load_data.py`. This will populate `datasets/raw_weather_data/` (or similar, depending on script configuration). 
* **1.2. Energy Production Data:**
    * Obtain hourly energy production data (ideally split by offshore/onshore if applicable) from your local grid operator, energy authority, or data provider.
    * Format the data into a CSV file with columns like: `Timestamp` (UTC), `Wind_Offshore_MW`, `Wind_Onshore_MW`.
    * Save the file(s) into `datasets/raw_energy_production_data/`.
* **1.3. Electricity Price Data:**
    * Acquire hourly wholesale electricity price data for your market/region.
    * Format into a CSV file with columns: `Datetime` (UTC), `Price` (e.g., $EUR/MWh$).
    * Save the file to `datasets/energy_price/your_region_wholesale_electricity_price_data_hourly.csv`.

**2. Data Preprocessing**

* **2.1. Preprocess Weather, Energy, and Price Data:**
    * Run the main preprocessing script. You might need to adjust paths and data types based on your specific files. Example calls:
        ```bash
        python data_processing/preprocess_data_script.py --data_type weather --input_dir datasets/raw_weather_data --output_dir datasets/processed_weather_data
        python data_processing/preprocess_data_script.py --data_type energy --input_dir datasets/raw_energy_production_data --output_dir datasets/processed_energy_data
        python data_processing/preprocess_data_script.py --data_type price --input_dir datasets/energy_price --output_dir datasets/processed_price_data
        ```
    * This performs time zone alignment, cyclical encoding, and missing value handling.
* **2.2. Combine and Aggregate Weather Data:**
    * Execute the combination script (you may need to configure input paths/logic within the script based on your processed weather files):
        ```bash
        python data_processing/combine_data.py
        ```
    * This typically generates aggregated weather files like `combined_onshore_weather.csv` and `combined_offshore_weather.csv` in a processed directory.
* **2.3. Create Final Unified Dataset:**
    * Run the stacking script to merge all processed data streams:
        ```bash
        python data_processing/stack_energy_data.py
        ```
    * This creates the primary dataset (e.g., `datasets/final_datasets/combined_total_energy_data_YYYY_YYYY.csv`) used for model training.

**3. Wind Power Prediction Model (Stage 1 - TCN)**

* **3.1. Configure Model:**
    * Review and adjust parameters in `wind_power_prediction/config.py` (e.g., `SEQUENCE_LENGTH`, feature lists, TCN architecture settings) based on your data and requirements.
* **3.2. Hyperparameter Tuning (Optional but Recommended):**
    * If compute resources are available (like Azure ML or locally), run the tuning script:
        ```bash
        python wind_power_prediction/azure_hyperparameter_tuning.py \
           --energy_data <path_to_final_energy_data.csv> \
           --onshore_weather <path_to_combined_onshore_weather.csv> \
           --offshore_weather <path_to_combined_offshore_weather.csv> \
           --output_dir wind_power_prediction/tuning_results/
        ```
    * Update `wind_power_prediction/config.py` with the best hyperparameters found.
* **3.3. Train TCN Model:**
    * Execute the main training script. Specify the start date for training data (replace 2020-01-01):
        ```bash
        python wind_power_prediction/main_train.py --start_date 2020-01-01
        ```
    * This loads data, preprocesses it (including capacity proxy calculation and normalization), creates sequences, trains the TCN, and saves the best model (`.keras` file) and scalers (`.joblib` file) to the `wind_power_prediction/` directory.
* **3.4. Generate Wind Production Predictions (Inference):**
    * Run the inference notebook/script. This example uses `nbconvert` to execute a Jupyter Notebook:
        ```bash
        python -m jupyter nbconvert --execute --to notebook --inplace energy_price_prediction/wind_generation_tcn_inference.ipynb
        ```
    * Ensure the notebook loads the correct trained model and scalers.
    * This generates a CSV file (e.g., `energy_price_prediction/stage1_predictions_mw_model_trained_from_2020-01-01.csv`) containing the predicted offshore and onshore wind power in MW.

**4. Electricity Price Prediction Model (Stage 2 - XGBoost)**

* **4.1. Prepare Features for Price Model:**
    * Open and run the `energy_price_prediction/xgboost_price_prediction.ipynb` notebook.
    * The notebook handles:
        * Loading Stage 1 wind predictions.
        * Loading processed electricity price data.
        * Merging these datasets by timestamp.
        * Creating necessary time features (hour, day, month, etc.).
        * Generating lagged price features (e.g., price_lag_1h, price_lag_24h).
* **4.2. Train XGBoost Model:**
    * Within the same notebook (`xgboost_price_prediction.ipynb`), configure the XGBoost parameters (adjust `XGB_PARAMS` if needed based on tuning or experimentation).
    * The script performs a chronological train/test split (e.g., train on data up to a certain date, test on data after that date).
    * Train the XGBoost model using the prepared features. Early stopping will be used based on validation performance.
    * Save the trained model, typically as a `.json` or `.ubj` file:
        ```python
        # Inside the notebook
        model.save_model("energy_price_prediction/final_xgboost_price_model_tuned.json")
        ```
* **4.3. Evaluate Model Performance:**
    * The notebook includes steps to evaluate the trained XGBoost model on the test set:
        * Calculate MAE and RMSE metrics.
        * Compare results against baseline models (persistence, average).
        * Visualize predictions versus actual prices.
        * Analyze feature importance plots to understand model behavior.
